# 도면 작성·관리

도면을 만들거나 편집·갱신·배치·출력하는 Step에서 적용한다. 공간을 읽고 표현 목적·범위·축척을 정하는 기본 원칙은 BASIC을 따른다.

## DR1. 무엇이 설계 원본인지 정한다

직접 설계한 2D 선, 모델에서 생성한 도면, 검토 주석을 구분하고 이번 변경이 어느 원본에 반영돼야 하는지 정한다. 2D 편집이 설계 제안인지 모델 변경을 반영한 도면 정합인지 밝힌다. 모델과 도면의 관계를 결정하지 않은 채 한쪽 편집만으로 양쪽이 갱신됐다고 보고하지 않는다.

3D 원본에서 도면을 얻는 과업은 그 원본과 생성·갱신 경로를 유지한다. 순수 2D 설계에는 존재하지 않는 3D 모델을 요구하지 않는다. 서로 다른 제작 경로를 사용하는 경우에도 현황·제안·생성물·주석의 역할을 알아볼 수 있게 남긴다.

## DR2. 재생성 전에 수동 편집의 의도를 보존한다

원본이나 절단 조건이 바뀌면 생성 도면과 그 위의 수동 편집 중 무엇이 유효한지 판단한다. 도구가 보존하는 범위는 현재 계약에서 확인하고, 재생성으로 사라질 수 있는 설계 의도·주석·보정은 식별해 둔다. 이전 선을 무조건 복원하지 말고 새 원본에도 필요한 내용만 다시 연결한다.

대안 도면·비교 자료와 현재 전달 도면을 구분한다. 같은 이름이나 같은 Layout에 있다는 사실로 최신성을 판단하지 않는다. 원본 변경 뒤 갱신하지 않은 관계가 있으면 해당 도면의 사용 한계를 함께 밝힌다.

## DR3. 전달 형식에서 판단이 유지되는지 확인한다

모델이나 ModelSpace에서 읽힌 관계가 Layout·출력물에서도 읽히는지 확인한다. 배치·축척·잘림·선 위계·주석이 달라졌다면 전달물에서 다시 본다. 검토할 레벨·치수·절단 위치는 그림의 해당 위치와 연결하고, 출력 형식이 증명하지 못하는 인쇄 속성은 검증했다고 하지 않는다.

`drawing` 흐름처럼 검수 뒤에 Layout·export Step이 있어도, 그 Step에서 생긴 잘림이나 표현 손실은 전달 전에 해결한다. 결과 파일 생성은 사용자가 의도한 관계를 읽을 수 있는 도면이 완성됐다는 근거가 아니다. 질문과 대안을 전달할 때는 `feedback_reporting` policy를 함께 적용한다.
