# ontological_holon registration and document alignment

An Ontological_Holon is an explicitly registered meaning unit bound to a persistent Rhino group GUID. Ordinary groups and reusable block definitions remain ordinary modeling structure. Names, layers, group indices and copied object metadata are not registration identities. The five registry tools use `ontological_holon`/`ontological_holons` in their callable names. Public fields use `holon_id`/`holon_ids`, `parent_holon_id`/`child_holon_ids`, and `holon`/`holons` envelopes. Plan detail uses `include_holons`; focus uses `focus_holons`. Holon-specific overlap queries are not exposed. For overlaps, use rhino_group_id with get_objects(scope="document", group_ids=[...], include_ids=true), then pass the document object GUIDs to get_object_intersections. Internal store projections and native serialization retain their older spelling so saved Rhino registrations and historical ID values remain unchanged.

## Document truth and metadata

The current stable Rhino group, its actual top-level members and its current name are geometry truth. Group members can include block occurrences and annotations; shared block-definition geometry is not a document-level member. Alignment never creates geometry or groups, changes membership or group order, renames groups, changes selection or view, or writes management attributes on objects.

A document-private registry in Rhino RuntimeData records the meaning handle, group GUID, required Scene context and explicit semantic child links. Actual members and direct ownership are derived from current groups and that explicit tree. An ordinary subgroup is not automatically a semantic child. Cross-document parents, multiple parents, cycles and unrelated direct ownership overlap are rejected. A parent group must already contain its declared children's actual members; registration does not normalize an architectural group to fit a ledger.

The registry is serialized through the Bridge plugin's WriteDocument/ReadDocument hooks. Registry changes use a custom Undo event for private plugin data. Registration updates, Scene-context changes and unregister remain undoable without member stamps. No-op inspection/alignment creates no native Undo record and does not modify the document.

Rhino group-table creation, deletion and rename are not native Undo-tracked. Upsert therefore rejects an existing group name mismatch before mutation; use the group's current name. This intentionally narrows the former rename behavior instead of claiming that a semantic Undo also restores a native group name. Manual Rhino name changes are observed by query/alignment. When an explicitly created group's registration is undone, native object Undo restores the original object attributes and membership, while the group table retains an empty entry and the semantic identity becomes inactive. Redo restores membership and registration over that same GUID. A later creation request whose name collides with any live group, including that empty entry, is rejected before mutation instead of accepting Rhino's automatic numeric suffix. Review the ordinary group or explicitly choose a different name; automatic membership repair or replay is never implied. The custom Undo callback never mutates Rhino groups or geometry. A group deleted through the raw group-table API remains missing until Rhino actually restores it, for example through explicit Undelete. Undo of an actual object deletion restores live members normally. See McNeel's [group Undo explanation](https://discourse.mcneel.com/t/c-undo-doc-group-delete-after-command/42542/2) and [custom Undo restrictions](https://developer.rhino3d.com/samples/rhinocommon/custom-undo/).

Legacy almond:component_record values are read once for migration. Invalid or conflicting legacy entries are isolated. Valid DB bindings can seed absent document identities, including after a document was saved before its first alignment. Neither migration nor seeding recreates a missing group. Existing document records and explicit unregister/Undo tombstones always win over DB seeds. Existing legacy stamps and unrelated user attributes are preserved byte-for-byte.

Archive writes serialize private state only; they never initiate legacy object observation during Save. The archive preserves whether first stable migration is still pending. Only a normal Open reads a document registry; import, insert, template/new, references and unknown read modes preserve the current registry. Each migrated/seeded identity must fit the 4 MiB archive budget before private state changes; an oversized item becomes an isolated problem and cannot break the next Save. Legacy conflicts remain explicit problems even when a DB binding can recover the missing identity.

## Agent tool behavior

- `upsert_ontological_holon` retains its explicit member inputs. Omitting `object_ids` or passing null requires a supplied group GUID or an existing Holon's group binding. The same native operation reads current group members, excludes explicitly declared child members from direct ownership, and validates the proposed ownership snapshots before mutation. The group must exist with 1–4096 valid members; inference never creates a group or infers name, Scene context or semantic children. Explicit `[]` continues to mean zero direct members. An existing supplied group must match its current name and actual direct/declared-child member set. With explicit IDs and no group GUID, one exact matching ordinary group is adopted; several matches require an explicit GUID. Only an explicitly requested new meaning group may be created. Upsert is not a geometry replacement, rename or membership-repair tool.
- `get_ontological_holon` reads a cached snapshot or an explicitly requested live observation. `recursive=false` is the public default; IDs are hidden by default. Detailed geometry and reference fields are opt-in through the query projection.
- `list_ontological_holons` supports Scene scope and defaults to top-level registrations. A Holon directly associated with a Scene remains visible there when its parent is associated only with another Scene. Recursive Scene queries expand those canonical roots while preserving every descendant's own Scene context.
- `sync_ontological_holon` keeps the existing single `holon_id` form and also accepts `holon_ids` or one `scene_id`. Omitting a target aligns the bound document. The ID is consequently no longer a required schema field. Do not combine target forms. One tool call observes a bounded scope once and returns checked/changed/unavailable counts, item-specific problems and necessary revisions, not full native snapshots. Explicit parent scopes include registered descendants. Scene scope also discovers native registrations missing from the DB and includes their descendants; an explicit ID scope never broadens this way. Scopes above 64 registrations or the native 2 MiB response bound require narrowing.
- `remove_ontological_holon` unregisters meaning while preserving the ordinary group, all geometry and object attributes. A child must be detached first; existing Plan/Step references must be reconciled before explicit unregister. Children of an unregistered root remain registered roots.

All Holon bridge calls require `component_registry=2` as well as the existing design_components capability. Old RHPs fail before new registration work, so a new Python worker cannot silently reintroduce object stamps through an old native implementation.
Only omitted/null-member upserts additionally require `component_group_inference=1`; a Bridge without it is rejected before registration. Existing explicit-ID calls continue to use `component_registry=2` without the new capability. Complete snapshot, identity, exclusive ownership and hierarchy validation still precede DB writes; an invalid response after a native attempt requires reconciliation and is never replayed automatically.

## Stable observation and DB agreement

Group/block editing isolation, an unknown editing target, active native command or Undo transition, unavailable document state and unsupported editing providers cannot authorize alignment. `EditingContext.Observe(doc).stable` must be true. InCommand=0 alone does not prove ordinary model editing.

Batch native observation returns complete snapshots plus isolated problems. Missing or incomplete identities cannot erase cached state. Each successful snapshot is validated for document and group identity, Scene context, hierarchy, complete membership, finite bounds and exclusive direct ownership before the transaction commits. One invalid registration does not prevent unrelated valid groups from being observed. Missing groups have availability=missing_group with no active cached members; their meaning identity and references remain so Rhino Undo can restore the binding. This differs from explicit semantic unregister, which keeps an inactive registry identity and is itself undoable.

Scene membership may include ordinary top-level Rhino objects and clipping planes as well as semantic groups. The `scene_object_membership` table stores per-model direct GUID memberships and exclusions; it does not cache geometry or change group ownership. `add_scene_objects` and `remove_scene_objects` process GUID arrays in order and report only zero-based failed and already-present/already-absent indices. Removing a group member from a Scene creates an exclusion without editing its group. `get_scene_objects` combines verified group members and directly registered objects, subtracts exclusions and deduplicates by GUID; missing directly registered objects make the query fail until their membership is removed. Cached Scene object counts are null when overrides exist because exact deduplication requires live observation; `direct_objects` counts direct registrations. Component-specific list and sync remain semantic-only. Older workers must be stopped before using this schema and cannot safely interpret direct memberships.

If Scene discovery finds a native child whose parent is not cached and is outside that Scene, alignment rejects before all DB writes with `component_scope_incomplete`, `missing_parent_holon_ids` and a concrete next action. Align the listed parent IDs or their Scene first, then retry the child Scene; Scene discovery never silently expands into ancestors in another Scene. These recovery cases preserve every cached row until complete scoped proof is available.

SQLite is a cache and reference ledger. Geometry changes and native Undo are separate from a DB transaction. A native mutation followed by a lost response or failed DB commit remains uncertain; do not replay it. Read current registry/groups and align explicitly. A consistent repeated alignment leaves revisions unchanged.

Explicit Scene context is stored in the FK-backed `ontological_scene_context(ontological_id, scene_id)` table; canonical Scene roots use `scene_ontological(scene_id, ontological_id)`. The context preserves each child’s originally requested Scenes when an ancestor is the canonical Scene root. A referenced context Scene cannot be deleted. Scene references contain only a requested ancestor when that same Scene already includes it; descendants retain their own original context without inheriting another Scene from the parent. Parent detach, semantic Undo and Scene changes recompute canonical links. Plan Holon references similarly discard requested descendants only when a requested ancestor is present. A child-only target remains a child-only target.

When a child-only observation changes geometry or hierarchy, unobserved old/new ancestors are marked `effective_summary_stale`. Cached reads then return null effective counts/bounds and `requires_sync=true`; observing the parent clears this flag. Direct group counts remain last-observed summaries. Selected-object ownership is observed live, while ancestor/Plan references remain DB evidence (`references_live_verified=false`).

## Verification

Intersection observations resolve current document-level objects or optional nested block occurrences without changing their definitions. Brep/Extrusion pairs use the Brep kernel; Mesh pairs use the installed Rhino mesh Boolean API, preserving disconnected shells as one operand. Mixed pairs report temporary Brep meshing as an approximation. Invalid/open or unoriented geometry and unconfirmed kernel results remain unsupported or unknown.
The continuation cursor binds the ordered candidate set to document identity, geometry, occurrence transforms and tolerance. The restored Holon query retains its pair handles/state as observation evidence. The unified review tool uses current top-level object IDs and does not require those state receipts.

`resolve_object_intersection` owns a connection-local review scope. Start with object_ids and optional include_block; it stops at the first positive pair, recomputes that pair and returns a context/isolated comparison plus numbered object metadata. Public `show_object_intersection` is removed. The camera/selection follow the targets; native Isolate/Unisolate supplies the second image, retaining locked context and checking that original visibility returns. Blocks are shown as top-level instances with member position markers and containing block names/paths. Metadata is bounded and marks omissions.

The next call uses review_id plus choice 1/2 to trim only the overlap from that numbered object, or skip. The review ID binds displayed identities, not a stale geometry snapshot. Each choice re-resolves operands and recomputes the current overlap. The existing executor owns one validated replacement and Undo record; GUID, attributes and group membership are preserved. Disconnected Mesh results stay one object. Block/source-file edits, mixed representations, unpreservable geometry attributes and whole-target deletion remain unsupported. A successful choice is reported in previous_result before scanning the current scope again; later review/capture failure does not erase the successful edit receipt. Repeated/superseded IDs are rejected and uncertain mutations block automatic continuation. No model save, source-asset change or semantic Holon registration occurs.

Store/public-tool BDD uses disposable SQLite and the existing external native callback seam. Native fixtures use actual disposable Rhino documents to compare geometry, ordinary groups, group order, attributes, Modified and Undo state, plus registration/unregister Undo/Redo and group-delete/Undo behavior.

The test-only SemanticRegistryFixturePlugin has its own GUID and forwards to the same production archive helpers. It can verify real 3dm plugin-hook roundtrips in a separate empty Rhino UI process without replacing the everyday Bridge registration. That verifies shared serialization behavior, not that the everyday production RHP was registered or loaded. Build, output placement, registration, actual load and modeling verification remain separate evidence.

A physical group GUID cannot have two semantic registrations. The former implicit zero-direct-member parent over a single child created an identical-member wrapper group; that automatic duplicate creation is now rejected. Supply a separate actual parent group whose current structure supports the intended meaning, rather than inventing a wrapper from a cached child list.

## SQL storage and migration

Opening an `ontological_components` database renames that registry to `ontological_holons` in the initialization transaction. SQLite updates dependent views, triggers and foreign keys; stable IDs, row payloads, Scene/Plan links and historical snapshots are preserved. Mixed old/new registries are rejected. Back up a live project DB and close its old workers before applying this change; old SQL clients must not continue against the renamed schema.

The physical registry is `ontological_holons`, keyed by `ontological_id`. Its `project_file_id` references `project_files(file_id, file_name)`; filenames are display values and UUIDs are stable keys. `_project_file_locations` privately maps each file key to a normalized saved model path. Equal filenames in different directories remain different identities. The private native/store `component_id` spelling stays compatible through internal read-only projections; the public boundary exposes `holon_id`; writes and FK relationships use the physical ontological columns.

Plan targets use `generation_plan_ontological` and reference real semantic IDs. Steps have no independent Component assignments; target resolution uses their Plan. Legacy Step targets are retained in `_retired_step_targets` during migration and removed from active `generation_step_ontological` relations. Parent links require the same file and prohibit cycles. Scene and Phase can reference the same project_files keys. Unspecified files are NULL references and display as an empty filename.

On first legacy migration, populated DBs receive a uniquely named `*.before-object-retirement-*.bak` backup. A reserved SQLite write transaction copies semantic identities and relations, computes group summaries, removes per-object rows and retired direct Scene links, and verifies all foreign keys before commit. Historical Scene revision object ID arrays are removed from the active ledger; the backup retains the original history. Invalid relationships or mixed old/new schemas stop without partially migrating. All old workers must be closed normally before deploying the new schema; do not reopen a migrated DB with older source. A rollback requires the backup together with the matching old source.

The obsolete `_component_records`, `_scene_component_refs`, `_plan_component_refs`, and `_step_component_refs` views are dropped during store initialization. Relationship reads use their canonical tables directly. Holon reads use a shared static SELECT over the canonical tables rather than a persisted compatibility view. This does not delete Holon records, change stable IDs, or rename the native serialization contract. Stop older workers before opening a shared DB with the updated store: an already-running old worker still expects the removed views. Reopening with old source can recreate it; deploy the updated Python readers together.
