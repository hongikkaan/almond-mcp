# 설계 세션 회고와 개선

동지는 여러 설계 세션의 개선을 조율한다. 개별 모델의 설계와 도면 제작은 각 세션이 [RhinoBeyond](../rhinobeyond/SKILL.md)로 진행한다. 이 스킬을 읽었다는 사실은 코드 수정, 실제 Rhino 사용, 커밋·병합의 승인이 아니다. 현재 요청에서 허용된 단계까지 진행하고 이미 받은 승인은 다시 묻지 않는다. [운영 합의 정본](https://app.notion.com/p/41ce0a39412081bd9b02c4e1bb928383)

글로벌 설치본에서 읽을 때는 일상 Almond 저장소(Windows 기본 위치: `C:/TOOL/Rhino/mcp/almond-mcp`)를 먼저 확인한다. 패키지 밖 상대 링크는 저장소의 `.agents/skills/almond-evolving/SKILL.md` 위치를 기준으로 열고, 검토안 양식은 이 스킬에 동봉된 파일을 쓴다.

## 회차 시작과 Slack

익환이 ‘세션 끝났다’고 알리면 해당 설계 회차의 로그와 세션별 피드백을 직접 찾아 회고를 시작한다. 진행 중에는 자료 수집과 분석을 병행하되 종료한 것으로 간주하지 않는다.

합의한 Almond 채널에 설계 스레드와 별도로 해당 회차의 개선 스레드를 짧은 제목으로 한 개 열고 첫 댓글에서만 익환을 한 번 태그한다. 이미 해당 회차의 개선 스레드가 있으면 재사용한다. 관련 설계 세션·Action·기존 피드백 링크를 그곳에 연결하고, 검토안·논의·결과를 같은 스레드에 이어서 남긴다. 다시 열어 이미 제출한 문서를 편집해야 하면 편집 전에 익환에게 알린다.

## 오전 설계와 휴식 중 검토

1. 각 설계 세션은 현행 모델과 기존 Plan·Loop를 확인하고 익환과 이번 **Goal·실행 범위**를 맞춘다. 한 번에 회고할 수 있을 만큼 진행한다. 전후 도면·모델에서 무엇이 바뀌었고 어디에서 막혔는지 보이면 충분하다. 익환은 필요한 설계 판단과 Loop 말미의 결과 피드백을 맡는다. 공정 개선은 메모해 두고, 지금 설계를 막는 문제만 즉시 다룬다.
2. 동지는 두 단계로 고찰한다.
   - **1차 · 독립 로그 분석.** 익환이 별도 회고용으로 남긴 피드백과 인박스를 열기 전에 세션 원본 로그·툴 호출과 응답·산출물·당시 지침을 대조한다. 세션 안에서 주고받은 지시와 수정은 실제 사건으로 읽는다. 에이전트가 한 일, 결과, 내 판단과 미확인을 먼저 기록한다. 이미 별도 피드백을 본 경우 독립 검토라고 쓰지 않는다.
   - **2차 · 피드백 대조와 재고찰.** 1차 판단을 기록한 뒤 익환의 피드백과 관련 인박스 원문을 읽고 같은 로그에 대조한다. 진단을 사실로 받아들이지 말고 반례와 다른 원인을 찾는다. 새로 발견한 내용과 유지·수정·유보한 판단의 이유를 기록한 뒤 개선안을 작성한다.
   - **개선 검토안을 쓰기 전에** 익환의 세션별 피드백 원문(Action·Slack 등)과 [Almond Actions](https://app.notion.com/p/81d601b1051c4eacad958a136083c723) 인박스, 이번 회차와 관련된 다른 인박스의 원문을 함께 읽는다. 인박스 상태만 보지 말고 후속 결정·기존 조치·실제 세션 기록과 대조한다. 같은 문제는 한 안건으로 묶되 피드백과 인박스의 근거를 모두 연결한다.
   - 이번에 다룰 안건, 일부 반영돼 남은 범위, 검수만 남은 항목을 나눈다. 이미 적용된 것은 재발을 판단할 비교 근거로 쓰고, 기각·보류된 안은 새 제안으로 되살리지 않는다. 최신 합의와 충돌하거나 원문을 확인하지 못한 항목은 미결 이유를 적는다. 개정 뒤 재발했다고 쓰려면 해당 세션이 실제로 그 개정판을 사용했는지 확인한다.
   - 회차 심층고찰은 해당 회차의 기존 Notion Evolving Action 한 곳에 세션별 섹션으로 [Notion 회고 양식](references/notion-wrapup-template.md)으로 정리한다. 각각 원본 세션과 근거를 연결하고 세션별 회고 페이지를 새로 만들지 않는다. 설계 결과·피드백과 별도로 실제 호출 순서·판본·도구 선택·복구·비용을 대조한 **툴 사용 검수**를 남긴다. 개선 후보만 아래 저장소 검토안으로 연결하고, 확인되지 않은 동작이나 비용을 채워 넣지 않는다.
3. [검토안 양식](references/review-template.md)으로 저장소 루트의 `개선할 거.md`를 작성한다. 같은 회차 문서가 있으면 재사용하고, 이전 회차 문서가 남아 있으면 해당 회차와 현재 변경 상태를 확인한 뒤 새 회차로 갱신한다. 익환이 편집 중이면 덮어쓰지 않는다. 기대한 동작과 관찰한 결과가 어디서 갈렸는지 적는다. 그 근거가 없으면 관찰한 현상과 남은 질문까지만 쓴다. 한 세션의 시행착오를 모든 설계에 적용할 규칙으로 만들지 않는다.
4. 검토안을 같은 Slack 스레드에 공유한다. 익환과는 루트의 같은 문서를 보면서 영향이 크거나 판단이 필요한 안건부터 논의한다. 동지의 해석, 바꿀 문장, 재시험 기준을 익환과 조정하고 결정된 내용만 합의로 표시한다. 관찰을 더 하기로 했으면 다음에 볼 장면을 남긴다. 이미 합의한 결론이나 담당자가 자료로 판단할 사항은 다시 묻지 않는다.

## 합의 후 병렬 반영

| 담당과 위치 | 맡을 변경 |
|---|---|
| 동지 · 일상 Almond 루트의 `skill` | 설계 판단이나 작업 순서는 스킬·미니워크플로우에, 도구 선택과 필드 해석은 해당 도구의 description·입출력 스키마 주석에 반영한다. 같은 문구는 실제로 읽을 위치 한 곳에 둔다. |
| Codex · 기존 `dev` 워크트리 | 호출 결과·상태 전환 등 실행 동작은 코드에서 고친다. **Ask Matt → grill with docs → 합의 → to-ticket → 구현** 순서로 진행한다. 현행 문서·호출부에서 답을 찾고, 결정이 필요한 쟁점만 올린다. 티켓 사이에 공유 계약이나 선행 의존성이 있을 때만 공통 명세를 두고, 각 티켓의 수용 사례를 오프라인에서 검증한다. |

두 작업이 같은 파일을 다루면 먼저 담당 구간을 나눈다. 동지의 반영분이 최신 `skill`에 커밋되면 `dev`의 고유 변경을 보존해 그 위로 리베이스한다. 두 작업 사이에 `skill`만 앞섰다면 fast-forward로 맞출 수 있다. 충돌을 정리하고 영향받은 공개 호출·스키마와 회귀시험을 다시 확인한다. 위임과 검증은 [저장소 작업 지침](../../../AGENTS.md)을 따른다.

## 통합 검수와 마무리

- 코드·런타임 변경이 없으면 불필요한 dev 통합·빌드를 하지 않고, 스킬·설명 변경은 다음 설계 세션의 적용 기록에서 검증한다.
- 실제 검수 대상과 범위에 대한 허가를 확인한다. 일상 루트의 현재 브랜치·HEAD를 기록한다. 미커밋 사용자 변경이 있으면 보존하고, 깨끗한 루트에서 검수할 통합 커밋을 연다. 최종 소스와 일치하는 검증된 RHP 빌드가 없으면 루트에서 빌드한다. dev에서 이미 검증한 동일 빌드는 루트에서 배포 파일 해시와 manifest를 대조해 재사용할 수 있다. 빌드한 위치·커밋과 실제 검수 위치를 구분해 기록한다.
- [실제 Rhino 통합 검수 절차](../../../tests/README.md#실제-rhino-통합-검수)에 따라 별도 프로젝트·DB의 시험 모델로 새 Rhino를 띄운다. PID·시작 시각·문서와 두 RHP의 **실제 로드 경로**를 확인하고 같은 루트의 Beyond 공개 도구로 합의한 사례를 실행한다. 등록값이나 빌드 성공만으로 실제 동작을 통과 처리하지 않는다.
- 문제가 재현되면 시험 연결과 해당 인스턴스만 정상 종료하고 `dev`에서 수정한다. 필요한 빌드·오프라인 검사와 실제 Rhino 재시험을 거친다. 검수를 마치면 시험 연결·Rhino 종료와 원래 등록을 확인한다. 병합이 승인됐고 수용 기준을 충족하면 루트를 `skill`로 복귀시켜 검수한 `dev` 변경을 커밋 하나로 squash 병합한다. 부모가 직전 `skill`인지, 최종 트리가 검수본과 동일한지, 작업 상태가 깨끗한지 확인한다. [워크트리와 squash 검증](../../../tests/README.md#작업-워크트리와-squash-검증)
- RhinoBeyond 스킬 변경이 최종 `skill`에 반영되면, 일상 루트의 `.agents/skills/rhinobeyond`를 원본으로 현재 환경의 **글로벌 RhinoBeyond 설치본**을 교체한다. Windows의 기존 설치 위치는 `$HOME/.agents/skills/rhinobeyond`다. 실제 설치 위치와 원본·대상 경로 범위를 확인하고, 스킬 전체의 파일 목록과 내용 차이를 대조한다. 글로벌에 독립 수정이 있으면 덮거나 삭제하기 전에 확인한다. 다른 스킬은 건드리지 않으며, 교체 뒤 파일 목록과 해시가 원본과 일치하는지 검증한다. RhinoBeyond 스킬 변경이 없다면 교체하지 않는다. 설치 확인과 기존 세션에 새 지침이 로드됐는지는 구분한다.
- 같은 회차의 Evolving Action과 Slack 스레드의 완료 보고에 **구현자, 빌드 여부와 대상, 실제 Rhino 결과와 근거, 최종 커밋, 글로벌 스킬 교체 여부**를 남긴다. 오프라인에서만 확인한 사례와 남은 문제도 표시한다. 다음 설계 세션에서 같은 현상이 재발하거나 기대한 변화가 없으면 기존 안건을 다시 연다.
