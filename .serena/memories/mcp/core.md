# Python MCP와 연결 실행기

- `src/mcp/startup.py`의 `create_server`는 명시적 DB·라이브러리 경로와 전송 함수를 받아 서버별 `FeatureContext`를 조립한다. `server.py`·CLI·bound runtime은 이 생성 경계를 사용하며 import만으로 DB나 라이브러리를 초기화하지 않는다. `tool_declarations.py`는 실행 등록과 같은 기능 목록에서 선언을 읽어 BASIC 이름 목록과 외부 catalog에 제공한다. `store_database.py`는 SQLite 연결과 초기 DDL부터 최종 FK 검사까지의 쓰기 트랜잭션을 소유하고 `AlmondStore`는 기능 저장소 인터페이스를 유지한다. `src/mcp/runtime`은 checkout CLI·세션 바인딩·저장소·Rhino 문서 실행기이며 외부 연결기에 공개 구성 훅을 제공한다. Python MCP가 외부 연결기 구현을 import하지 않는다. 상세 경계는 `src/mcp/SPEC.md`를 따른다.
- 모델링·도면·Scene/Component·Plan·자산의 책임과 계약은 `src/mcp/SPEC.md`와 기능별 문서. 고정 조회와 일반 수정 실행은 `src/mcp/rhino/OBSERVATION-SPEC.md`를 따른다.
- Rhino 문서 전용 실행기와 beyond host는 공용 `modeling_guidance.py`를 통해 `initialize.instructions`에 서버 소개·기술 자료 조회 방법·`guide_version`만 전달한다. 설계 작업 지침은 별도 RhinoBeyond 스킬에서 관리한다. 독립 서버는 `context_01-get_policy` tool로 도구 목록과 기술 참고 자료를 제공한다. 공개 도구 설명·입력 안내는 등록 함수의 docstring에서 `tools/list`로, 동적 후속 안내는 `tool_guidance.py`에서 응답으로 전달한다.
- `context_01-get_policy` tool의 `policy="metadata"`는 `modeling_policy.json`의 객체 키 사전(`policy`)을 반환한다. 편집 지침은 `.agents/skills/rhinobeyond/policy/metadata.md`에 있다. 현재 공통 키는 접두사 없는 이름을 사용한다. `inspect_02-get_objects` tool의 `fields=["user_text"]`와 `filters.user_text`는 객체 속성 User Text를 대상으로 한다. `intersect_02-resolve` tool의 새 리뷰에 전달한 `user_text` 조건은 한 구성원이 모두 만족하는 쌍을 고른다. 저장 범위 및 기존 UserDictionary와의 구분은 `src/mcp/rhino/OBSERVATION-SPEC.md`를 따른다.
- 도면 레시피는 독립 서버와 문서 worker가 시작할 때 `paths.py`·`runtime/library_paths.py`가 선택한 폴더의 바로 아래 JSON을 파일명 순으로 읽는다. 명시한 사용자 폴더가 우선이며 체크아웃에서는 기본 AppData 경로가 전달돼도 저장소 레시피를 사용한다. `drawing_01-apply_style` tool은 ID 생략 시 첫 번째 로드된 레시피를 적용한다. 성공 응답의 PrintDisplay 안내는 레시피의 `review_preparation.print_display: true`로 결정한다. 작성·경로 계약은 `asset/drawing/DrawingRecipes/README.md`를 따른다.
- 도면 원본과 PlanSection 도면선은 `ModelSpace`에 두고 `PageSpace`는 Detail View와 시트 주석에 사용한다. Layout 검수의 객체 귀속과 보존 기준은 `.agents/skills/rhinobeyond/mini_workflow/drawing.md`를 따른다.
- 스크립트 도구의 정상 실행 상태는 `executed`다. `print` 로그와 `result`는 스크립트가 작성한 값이며, v1 완료 기록과 공개 상태의 대응은 `runtime/RHINOCODE-SPEC.md`를 따른다.
- 자산 준비의 `passed`는 확인한 단계의 검사 결과다. 등록 가능 여부, 기존 보고서의 해시 검증, 준비 작업별 잠금과 라이브러리별 발행 잠금의 구분은 `src/mcp/features/assets/SPEC.md`를 따른다.
- 프로젝트 초기 조회의 관찰 요청과 응답 조립은 `features/context/project_info.py`가 맡는다. 연결 설정은 바인딩을 확인한다. MCP 조회와 첨부 범위를 지정한 PlanSection 호출에서 사용하는 Worksession 정보는 Rhino의 읽기 전용 관측이다.
- 프로젝트 파일 카탈로그의 관계 키는 등록 파일명이다. `context_05-upsert_project_file` tool로 명시 등록과 설명 갱신을 하고 Phase와 Scene은 그 목록의 이름을 선택한다. Worksession 첨부는 Rhino에서 별도로 관찰하며 자동 등록하지 않는다. `drawing_06-generate_plan_section` tool의 `include_attachments`는 Create에서 기본 false, Update에서 생략하면 저장된 값을 사용한다. Move는 기존 도면의 GUID·수동 편집을 보존하며 배치만 바꾼다.
- `plan_12-update` tool은 `status="completed"`와 함께 받은 Step 필드를 한 DB 트랜잭션으로 저장한다. 완료 직전까지 같은 Loop와 revision인지 대조하며, 새로 완료된 경우에만 저장 확인 후 로컬 Temp 트리를 정리한다. 최상위 Temp와 Worksession 참조는 보존하며, 로컬 블록 정의에서는 해당 레이어의 구성원만 제거한다. 저장 후 정리가 실패하면 완료된 DB 상태와 별도로 `cleanup_state`와 `requires_reconciliation`을 확인한다. 상세 계약은 `src/mcp/features/planning/README.md`를 따른다.
- `tool_response.transform_response`는 조회 projection·후속 안내·경로 변환의 transport 처리를 공유하고 문자열 wrapper, meta·annotations, 이미지와 오류 근거를 보존한다. 자산의 선언·hash·경로 확인은 실제 제공 bytes에 적용하고 catalogue/MCP/배치는 공통 원본 선택 규칙을 따른다. 모델 자산과 다이어그램의 블록 배치 요청은 `features/assets/mutation.py`가 조립·전송하고, 파일 선택과 3DM 연결 지원 확인은 해당 도구가 맡는다.
- Workspace는 폴더 이동 intent와 동일 Loop transaction의 `workspace_loop_transitions` receipt로 미완료 전이를 복구한다. 작업 경로를 사용하는 호출은 공유 gate 아래 얻은 snapshot을 재사용한다. `runtime/owned_process`는 정확한 자식 identity 발행 뒤 부모가 명령을 승인하며 Python·Engine은 소유권/프로세스 종료와 native receipt를 별도로 확인한다. 공개 Loop API의 최종 응답 유실까지 exactly-once를 보장하지 않는다. 상세 계약은 `runtime/RHINOCODE-SPEC.md`.
- 구조의 `DesignAnalysis`는 요청 안에서 solved 상태를 재사용하되 11/13 station 및 buckling 의미를 보존한다. 새 native 해석은 한 설계기준 프로필로 하중 조합과 기본 처짐 한계를 결정하고 적용값을 이력에 남긴다. 기존 결과를 다시 표시할 때는 그 해석의 프로필을 유지한다. 분석 이력은 실제 적용 입력과 결과를 저장하고 legacy는 unknown으로 둔다. PlanSection은 추적한 변경의 보상을 계속 시도하고 recovery 근거를 반환하며 원자적 rollback으로 단정하지 않는다.
