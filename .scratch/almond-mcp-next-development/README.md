## 후속 실행 요청에 넘길 입력

`implement-spec`에 이 문서, spec.md, issues 디렉터리의 **절대 경로**를 함께 넘긴다. 티켓 워크트리는 명세·티켓 커밋을 포함한 통합 브랜치의 현재 커밋에서 시작한다. 새 워크트리의 HEAD와 병합 기준을 확인하고, 별도 브랜치에서 구현과 오프라인 검증을 진행한다.

- 구현이 요청되면 깨끗한 main에서 통합 브랜치를 만들고, 선행 티켓이 끝난 작업부터 티켓별 신규 서브에이전트·분리 워크트리로 배정한다. 이전 원격 PR·작업 브랜치에서 구현이나 diff를 가져오지 않는다.
- 기존 작업을 덮어쓰지 않는다. 독립 티켓은 병렬 진행하고 공통 파일 반영, 통합, 검수는 오케스트레이터가 순서대로 관리한다.
- 실제 충돌·오류·조정이 생기면 해당 티켓을 멈추고 [#almond 작업 스레드](https://app.slack.com/archives/C0CA8BC1SS1/p1794822493797419)에 현상·선택지·추천·영향을 올린다. 익환의 답을 받은 뒤 그 조치를 수행한다.
- 티켓별 개발 검사는 오프라인에서 한다. 오케스트레이터는 사용자와 범위를 합의하고 허가받은 뒤 [실제 Rhino 통합 검수](../../tests/README.md#실제-rhino-통합-검수)를 수행한다.
- PR 생성·push·main 병합·일상 환경 변경의 권한은 후속 요청의 범위를 따른다.

## 통합 검증

- 통합 브랜치는 `codex/almond-mcp-next-development`다. 12개 티켓의 구현과 명세·코드 기준 검토 수정은 `8037f90`까지 반영했고, 최종 RHP와 소스 대조 기록은 `890ec48`에 있다.
- 저장소 기준 검토에서 기본 도구 목록 누락, 블록 보존 확인, PlanSection 범위 기록 문서를 보완했다. 명세 검토에서 첨부 모델 식별 실패를 명시하는 경로와 유형별 메타데이터 안내를 추가했다.
- Rhino를 정상 종료한 상태에서 Bridge·AlmondRhino를 빌드하고 두 manifest와 공용 Engine DLL 일치를 확인했다. MCP 모듈 722개 통과, Windows 심볼릭 링크 설정 단계 6개 `WinError 1314` 실패, 당시 외부 연결기 76개와 루트 통합 19개 통과.
- PlanSectionHost를 다시 실행한 오프라인 검사에서 53개가 통과했다. 중첩된 부모·자식 블록 정의의 목록을 각각 필터링하는 Step fixture에서도 temp 구성원 제거와 남은 구성원·변환 보존을 확인했다.

### 실제 Rhino 통합 검수

- 워크트리 빌드를 로드한 Rhino에서 Beyond로 `test.3dm` 복사본을 검수했다. 새 시작 스크립트로 일상 등록을 즉시 복원한 뒤 같은 PID에서 워크트리 RHP·Engine과 Beyond 연결을 확인했다. 원본 `test.3dm`의 SHA-256은 검수 전과 동일했다.
- 모델·Layout·Named View·표시 모드와 메타데이터 필터의 유효 입력을 조회했다. 가로형·세로형·정방형 캡처에서 구체의 가로·세로 지름 차이가 최대 1px이었다. Layout 출력에서 파란 인쇄색과 서로 다른 인쇄 두께를 확인했고, Detail의 clipping이 적용된 형상만 사라졌다.
- A4 Recipe를 실제 문서의 9개 레이어에 적용하고 선종을 확인했다. 실제 모델의 PlanSection Create→Move→Update가 완료됐다. Worksession 참조를 붙인 시험에서는 PlanSection의 소스가 옵션에 따라 1개 또는 2개로 달라졌고, 모델 간 가림과 Update 시 범위 유지를 확인했다. 첨부 파일은 DB의 프로젝트 등록 목록에 추가되지 않았다.
- Step No에서 상태와 모델이 유지됐다. 새 요청에서 Yes를 선택해 하위 레이어 4개와 객체 9개를 제거했다. 최상위 `temp`, 중첩 블록의 배치와 메타데이터, 빈 블록 정의 및 외부 인스턴스가 유지됐다. Rhino SDK로 저장된 `.3dm`을 다시 읽어 블록과 최상위 레이어를 확인했다.
- 첨부 파일 소유 clipping plane과 다수의 대용량 첨부 성능은 이번 실제 검수에서 다루지 않았다.
