# 작업 범위·설계 검토·완료 근거

## 편집 범위

**편집 대상은 사용자 승인된 현재 Rhino 문서와 프로젝트 자료다. Worksession attached/reference 문서는 직접 수정하지 않는다.** 프로젝트 정보가 필요하면 `project_info`의 해당 sections만 조회한다. document 항목은 같은 호출에서 live 문서를 확인한다. 이를 다시 검증하려고 `get_rhino_context`를 호출하지 않는다. 상대경로의 기준은 실제 설정된 `ALMOND_PROJECT_ROOT`이며, 작업 산출물은 `set_working_plan`으로 선택한 `tmp/YYMMDD_작업명`이다. Python은 관리 실행 도구의 cwd, C#은 ManagedFiles helper를 사용한다. Rhino 전체 cwd나 TEMP를 산출물 기준으로 삼지 않는다.

**파일이 필요할 때만 만든다.** 재료 목록·레시피를 별도 `library.json`으로 다시 만들거나 작은 결과·전달 코드마다 중간 JSON/Python/C# 파일을 만들지 않는다. 공개 도구 응답과 메모리 변수를 재사용하고 작은 값은 `result`로 직접 받는다. 복구 백업·대량 비교·저장 검증·제출 이미지처럼 목적이 있는 파일은 위 artifact_dir에 두고 실행 시점과 완료 상태를 구별한다. 경로가 맞다는 이유만으로 불필요한 파일 생성이 정당화되지는 않는다.

등록·해제·정합은 공개 Component/Scene API로 수행한다. 공유 `DB`의 직접 UPDATE/DELETE, 소유권·`component_record` UserString 일괄 삭제로 오류를 우회하지 않는다. private reflection·임의 Idle 후속 변경·저장된 native 응답을 주입한 DB 갱신으로 공식 완료 확인을 우회하지 않는다. 작업 예약 성공은 그 작업의 완료가 아니다. read-only 조회와 직접 DB 변경은 구별한다. 현재 API로 안전하게 복구할 수 없으면 정확한 대상·오류·실제 반영 상태·남은 범위를 기록해 개발 문제로 분리한다. 다른 세션의 변경을 시작 snapshot으로 되돌리지 않는다.

## 작업 기준과 설계 검토

현재 지시에서 대상·보존 범위, 기준 도면/모델·좌표/그리드·레벨, 요구 상세 수준과 완료 조건을 짧게 정리하라. 이미 명확한 사항을 다시 질문하지 마라. 기존 계획과 최근 변경을 먼저 확인하고 필요한 자료만 찾아라. 현재 형상 판단은 현재 문서를 기준으로 하며, 과거 설명·결과 파일·사용자 표시 이름은 실제 상태와 대조한다. 현재 모델과 사용자가 지정한 기준이 충돌하면 차이를 드러내고 변경에 필요한 쟁점만 확인하라.

연결된 참조 모델은 필요한 대상을 켜고 끄며 접점과 소유 문서를 확인하라. 참조 파일을 고치거나 다른 담당자의 완료 보고만으로 접속이 해결됐다고 보지 마라. 사용자 답변의 전달문은 원 발언 확인 여부를 구분하고, 에이전트 자신의 보고·제안을 사용자 승인으로 읽지 마라.

현재 과업의 목적과 적용 조건에서 무엇이 문제인지, 어떤 상태를 달성·보존해야 하는지 판단하라. 관찰한 현상과 원인에 대한 가정을 구분하고, 그 판단을 확인하는 데 필요한 자료·측정·검수 방법을 선택하라. 과거 사례는 현재 조건과 비교할 참고 근거로 다루며, 당시의 문제 판정이나 해결책을 그대로 적용하지 마라.

수정 후보는 목표 충족 여부와 관련 요소·비대상 범위에 미치는 영향을 함께 검토하라. 하나의 현상을 없앴다는 이유로 해결됐다고 결론내리지 말고, 수정으로 바뀐 관계와 새로 생긴 문제까지 확인하라. 반복 적용은 검토한 조건이 성립하는 범위에서 수행하고, 조건이 달라지면 판단과 대응을 다시 검토하라.

사용자가 subagent를 금지하지 않고 관련 도구가 지원하는 설계 논의·크리틱·고찰은 다음 조건으로 읽기 전용 독립 검토를 수행하고 주 에이전트가 함께 검토한다.

- 현재 대상과 기준 시점, 평면·단면·수치 등 확보한 근거, 사용자 의도·고정 조건·요구 상세 수준, 구체적인 질문을 전달하라. 필요한 근거가 빠졌으면 주 에이전트가 확보한다.
- **읽기 전용, 편집 금지**를 역할에 명시하라. Rhino 형상·재질·선택·뷰·레이어, Scene/Room/instance·plan·DB, 작업 파일의 생성·수정·삭제를 모두 금지한다. 검토자는 전달 자료와 읽기 전용 조회를 사용하고 주 에이전트에게 의견으로 답한다.
- 위임 검토자는 주 담당자의 Plan과 준비된 검수 자료를 사용한다. Plan 갱신·Named View 저장·clipping·모드 준비는 주 담당자가 수행한다. 독립 과업의 Phase·Plan과 검수 화면 준비 규칙을 근거로 읽기 전용 검토자의 편집 범위를 늘리지 않는다.
- 조회 코드라도 `execute_rhino_script` 경로는 Undo 범위에서 실행되고 `List<Guid>` 반환에 자동 치수를 만들 수 있다. 재료 레이어 자동 후처리는 없다. subagent에게 일반 실행을 맡기거나 별도 Rhino·쓰기 연결을 열게 하지 마라. 연결 실패를 고치기 위해 설정·엔진을 변경하지 마라.
- 관찰 사실, 가정·누락 근거, 사용자 요구와의 충돌, 의미 있는 대안과 장단점, 제안하는 다음 확인을 구분해 달라고 요청하라. 자료가 없는 부분을 확인한 것처럼 결론내리지 마라.
- Component 구성 검토에서는 Scene의 행태·가치와 각 묶음이 가능하게 하는 역할, 포함·제외 이유, 비인접 기능 관계, 일반 group/block과 등록 Component의 구분을 검토 질문에 넣는다. 프레임·유리의 합침이나 개수·소유권 정합만 검토해 의미 기준을 놓치지 않는다.
- 주 에이전트는 제안을 현재 상태와 대조한다. 검토 중 모델이 바뀌었으면 영향받는 의견을 갱신한다. subagent 의견을 사용자 승인이나 구조 적합성 증명으로 취급하지 마라.

후속 작업이나 여러 요소에 영향이 큰 선택은 대안과 영향을 정리하여 사용자 방향을 확인한 뒤 본 모델에 반영하라. 사용자가 판단을 위임했다면 그 범위 안에서 선택하여 계속 진행하고 가정·선택·재검토할 지점을 마무리 보고에 남겨라. 이미 주어진 방향과 권한으로 해결할 수 있는 작은 보정까지 반복 승인받지 마라. 요청한 상세 수준과 범위를 넘는 작업을 임의로 추가하지 마라.

대안은 요청한 결정의 쟁점과 영향을 비교할 수 있게 구성하라. 비교 이미지로 질문할 때는 해당 이미지가 실제 보고 채널에 전달됐는지 확인하라.

검토자가 실행되지 않으면 미검토 쟁점을 기록하고 승인된 독립 작업을 계속하라. 필수 설계 판단은 검토 완료로 표시하지 말고, 실제 장애와 다음 판단이 필요한 지점에 도달했을 때 보고하라.

## 계획과 실제 완료 연결

**Phase 최소 1개 + Plan 생성·실제 사용은 필수다.** `list_phases`로 적합한 Phase를 선택하고 없으면 `create_phase`로 만든다. 새 독립 과업에는 `create_plan(..., phase_id=...)`을 호출하고, 같은 과업의 연속 작업에서는 기존 Plan을 조회·재사용한다. Phase 없는 기존 Plan은 `update_plan`으로 연결한다. API에서 Phase가 선택형이더라도 이 스킬에서는 누락하지 않는다.

필요한 Plan·대상만 조회하고 의미 있는 진행·중단·재개 시 `update_step`에 기록한다. 이미 읽은 정보의 반복 조회를 의무화하지 않는다. Plan에 대상 Rhino 문서와 관련 Scene을 식별하고, Room/instance 등록 범위는 현재 요구에 맞춰라. 결과·대상 핸들·검증 근거가 확보된 단계만 갱신한다. 사소한 수정은 관련 단계에 묶고, 독립 탐색·검토가 필요하면 상위 계획과의 관계·반영 조건을 기록하여 별도 Plan을 생성한다. 의존 단계와 revision을 확인한다.

기본 단계 이름이나 도구의 고정 scope가 과업과 다르면 실제 과업에 대응하는 목적·기준·해당 없음의 이유를 기록하라. 중단·전환·재개를 정상 상태로 다루고 `paused`를 사용하라. `depends_on`은 자유로운 관련 Plan/Phase ID 배열이며 완료나 순서를 강제하지 않는다. 미수행 단계를 완료로 꾸미지 마라. 도구가 지원하지 않는 과업은 남은 상태와 장애를 보존하라. 계획 완료는 모델·등록·검증의 증거가 모였다는 기록이다.

완료 판단에는 다음 중 요청 범위에 필요한 근거를 함께 사용하라.

- **실제 형상:** 요구 상태와 대상·보존 범위를 실제 형상·측정·관찰로 대조한 근거. 검사 결과가 무엇을 입증하고 무엇을 입증하지 못하는지 구분하라.
- **요청한 사용 목적:** 이번 과업에서 요구한 기능·성능·관계가 실제로 성립하는지 확인한 근거. 명칭이나 표현의 변경만으로 충족 여부를 판정하지 마라.
- **Almond 등록 범위:** Scene/Room/instance가 어떤 실물과 연결되며 무엇이 제외됐는지, 편집 뒤 참조·bounds·transform·검증 결과가 현재 상태와 일치하는지.
- **검증 범위와 한계:** 구조 가정과 하중·지지·단위·누락 조건, 기하 표본/공차/생략/unknown, 산출물과 저장 상태. 일부만 검사했다면 그 범위의 결과로 보고하라.

검수는 [시각 검수](visual-review.md)의 순서·범위를 따르고, 발견한 문제를 실제 형상·측정 결과와 연결하라. 뷰별 수정 또는 문제를 모은 일괄 수정은 과업에 맞춰 선택하라. Room/instance 갱신은 층·영역 등 정한 구간이 안정된 시점에 모아 처리하고, 아직 갱신하지 않은 등록을 최신 상태로 보고하지 마라.

형상이나 가정이 바뀌면 영향받은 검증을 다시 수행하라. 충분한 근거를 얻은 뒤에는 새 위험이나 필수 조건이 없는 반복 검사를 늘리지 마라. 사용자가 다음 영역으로 진행하도록 지정한 상세 수준·완료 기준을 존중하라.

긴 작업은 안정된 구간마다 저장하고, 최종 저장본에서 대상·보존 객체·등록·Named View와 clipping 복원 상태를 확인하라. 전후 비교는 같은 열거 범위와 기준 시점으로 하라. 숨김·참조·정의 객체의 포함 범위가 다른 개수를 비교해 유실 또는 보존을 단정하지 마라. 저장 성공은 설계·검증 완료와 구분한다.

`doc.Modified=false`를 직접 설정해 미저장 표시를 지운 뒤 저장 검증으로 제시하지 않는다. 저장 뒤 modified가 다시 true이면 원인과 저장 이후 변경을 확인하고 필요한 범위를 다시 저장·재읽거나 남은 미저장 상태를 보고한다. 일부 실물의 CRC·owner만 일치한다고 전체 재료·레이어·속성·뷰까지 저장됐다고 확대하지 않는다. 작업자의 수행·저장 완료와 사용자의 피드백·테스트 검수 완료도 구별한다.

## 오류·중단 후 결과 확인

도구의 바깥 응답만 보지 말고 내부 `status`·오류·경고를 확인하라. C#의 `status=success`와 `result_error`는 실행은 끝났으나 반환 데이터 변환에 실패했다는 뜻이며 그 이유로 변경이 롤백되지는 않는다. runtime/Undo 오류는 응답의 복구 결과와 현재 상태를 확인하라. 타임아웃·사용자 중단은 변경 없음이나 자동 롤백을 뜻하지 않는다. 대상 객체·등록 상태·진행 중 작업을 확인한 뒤 남은 작업을 결정하라. 결과를 회수하기 위해 성공한 변경을 재실행하지 마라.

등록 해제 등 선행 변경이 실패하면 그 성공을 전제로 한 그룹 삭제·재등록·장부 정리를 즉시 중단한다. 여러 호출을 묶는 코드도 매 응답의 내부 상태를 검사해 다음 변경을 차단한다. 오류 문자열을 출력한 채 루프를 계속하거나 Plan만 완료로 바꾸지 않는다. 공개 live 조회·가능한 공식 sync로 현재 상태를 확인한 뒤 나머지를 결정한다.

대량 객체·Worksession 참조 조회는 필요한 범위로 나누고 파일/정의별 공통 정보를 재사용하라. 응답이 없어도 이전 실행이 `running`·미확인이면 후속 변경을 겹쳐 실행하지 마라. 재개 시 마지막 저장과 실제 남은 상태를 확인하고, 충돌 원인은 확인된 호출·오류와 추정을 구분하라.

파일 결과는 실행 ID와 대상 문서가 일치하고 해당 실행에서 완성됐는지 확인한 뒤 사용하라. 고정 파일명에 남아 있는 이전 결과를 실패한 새 실행의 결과로 읽지 마라. 고정 probe는 같은 응답의 `status`·`probe`·`document` identity·`data`와 호출 완료를 대조하며 별도 manifest/run_id 파일을 만들지 않는다. 별도 파일이 필요한 스크립트에는 새 실행 식별자와 완료 상태를 남겨라. 출력 잘림·파싱 오류·파일 미생성은 완료 근거가 아니다. 범위를 좁히거나 같은 실행의 파일에서 필요한 부분을 회수하라.

중간 보고는 사용자의 의사결정이 필요하거나 질문할 때만 하라. 그 외 진행 내용과 결과는 묶어서 보고하라. 매 보고에 관련 시각자료를 최소 1개 첨부하고, 최종 보고에는 검수 결과와 남은 문제를 읽을 수 있게 시각자료를 취합하라. 완료·부분 완료·중단을 구분하여 실제 확인한 결과, 남은 설계 판단·검증 한계, 재개할 대상과 다음 단계를 남긴다. 사용자가 지정한 채널·스레드·멘션·질문 방식을 따르고 실제 첨부 전달을 확인하라.
